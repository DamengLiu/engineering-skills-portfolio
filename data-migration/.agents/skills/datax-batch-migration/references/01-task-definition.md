# 1 任务定义

从迁移目标和现有脚本出发，明确本批要迁什么、怎么调用、失败后如何推进。产出执行计划，供批量前检逐项核对。

## 1.1 识别入口

现有模块可能无参数启动，也可能接收批次号、日期区间或 history/actual 任务组。读取实际入口及调用链，只记录已支持的模式；不根据脚本名推断全量、预演或断点重传能力。

既有模块可使用固定任务列表、配置文件或共享入口，不为统一格式而改造。新生成的清单以“顺序 | Shell 脚本名称 | 启用 | 说明”为基础，需要按历史、当前等类别筛选时增加分组列；解析时去除字段首尾空白。顺序与脚本名应唯一，启用状态只用 `Y` 和 `N`。清单不重复保存字段映射、账号或 SQL。

## 1.2 圈定范围与推进策略

没有日期分片时，一张表是一个执行单元；有分片时，一个“单表 × 日期分片”是一个执行单元。为每个单元确定批次号、表名、任务组和起止范围。日期边界须有效；重叠或缺口需要已确认的业务原因。

默认串行执行，一张表失败不阻断其他独立表。同一目标表的后续分片是否继续，要看依赖关系。既有脚本遇错停止时，记录其真实策略与未执行任务；这些记录为日后按范围补传提供依据，不表示已实现自动重传。

## 1.3 形成执行计划

批次基线至少列出环境、任务数、执行单元数、参数模式、日期范围、失败策略和本次要求的检查。预计记录数、历史吞吐量等属于当前批次的事实，保存在批次目录，不写进 Skill。不能确认的内容标为“待确认”，不凭名称生成可运行脚本。

所有启用任务能定位唯一 Shell，范围与失败策略明确，才算任务定义完成；实际运行前还须确认环境、对象、范围和动作授权。并发、资源分组及补跑标识在有实际需要时再扩展。
