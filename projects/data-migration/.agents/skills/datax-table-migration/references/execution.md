# 2 迁移执行

本文件负责单表脚本生成、静态检查和按授权执行。脚本应像一份清楚的操作说明：先看到维护入口，再看核心流程，最后看辅助细节。

## 2.1 交付内容

每张目标表在同名目录中交付四类文件：

- `<target_table>_mapping.md`：需求确认阶段已保存的统一基线、确认记录和各来源五列字段映射；每个来源使用独立分节；历史 mapping 保持原名；
- `<source_table>_to_<target_table>.py`：每个来源一个作业，定义该来源查询、字段转换和目标写入；
- `<target_table>_migrate.sh`：依次执行前检、DataX 和迁移校验；历史入口保留原名；
- `<target_table>_check.sql`：供人工复核；按来源和目标表分块。

沿用项目现有配置和运行能力，不为同一来源额外生成重复作业、JSON 或同类脚本，不猜测服务器路径、驱动、账号、密码或环境地址。多个来源共用一个完整 Shell 入口和一份总核验 SQL。

新增 Python、Shell 脚本遵循项目级语言、命名、修改边界和验证规则。Python 内部标识符以 PEP 8 为准：函数、方法和变量使用 `lower_snake_case`，类使用 `UpperCamelCase`，常量使用 `UPPER_SNAKE_CASE`。DataX 迁移 Python 文件名按本文件定义保留源表和目标表业务标识，这是交付物命名例外。Shell 使用本节定义的专项接口命名。名称应表达实际业务含义，不使用含义不明确的缩写。历史脚本保持兼容，不因旧命名批量改造。

脚本按“任务说明与维护入口、常量与配置、核心流程、必要的辅助方法、执行入口”组织，让初级程序员也能快速找到映射、运行顺序和失败条件。注释说明业务目的、约束和失败影响，不逐行解释普通语法。修改前检查已有注释：保留有效的业务说明，规则变化时同步修订，纠正过时或错误内容，不因重排或重构轻易遗漏。可复用固定值优先使用现有常量载体；有限且有业务语义的状态优先使用现有枚举。只有出现真实复用需求时才新增常量或枚举，不为单个简单值创建形式化结构。

单表案例不写入 Skill。累计完成并真实验证至少 10 个单表案例前，不抽取公共运行层；允许四类交付物保留少量重复，以便独立部署、理解和排障。

## 2.2 mapping 文件

mapping 文件使用 [需求与字段映射](requirements.md) 中的迁移基线和五列字段映射格式，并至少记录：

- `需求确认完成`；
- 确认人和确认日期；
- 源表、目标表及可靠结构依据；
- 源业务键、目标业务键、目标物理主键和目标必填字段；
- 全量或增量方式、运行参数与源端筛选、目标写入与重跑策略、目标清理规则；
- 明确不迁移的源字段及依据；
- 未执行的数据库检查。

不另建一份脚本阶段基线；复用需求阶段的当前有效版本。多来源的执行顺序、覆盖规则和清理位置也以该文件为准。核验 SQL 的文件头写明源表、目标表、执行环境与执行顺序；每个来源单独说明校验块和阻断条件，目标表核验与跨来源合并规则另列分块。

## 2.3 Python 作业

按以下顺序组织：

1. 任务说明、维护入口、常量与运行参数；
2. 源端查询与字段转换；
3. 目标表、写入字段和清理配置；
4. 单表前检与校验定义；
5. 必要辅助函数和 现有迁移平台/DataX 执行入口。

文件开头写明维护入口：

```python
"""
迁移任务：源表 → 目标表

维护入口：
1. 字段映射：修改 SOURCE_QUERY 和 TARGET_COLUMNS
2. 运行范围：核对 SOURCE_QUERY 的筛选与实际参数
3. 写入与清理：核对 Writer 配置和 PRE_SQL
4. 数据校验：修改 VALIDATION_QUERIES
"""
```

具体要求：

- Python 代码遵循项目级 PEP 8 规范；
- 禁止 `SELECT *`；
- 源查询与 Writer 字段按位置一一对应，数量、顺序和含义一致；
- 目标字段必须存在于可靠表结构中，别名宜与目标字段一致；
- 固定值、空值、日期转换和长度处理清楚可见；
- 禁止截断、舍入、裁剪、静默去重或用默认值覆盖有效来源数据；
- 字段变化时同步检查映射、查询、Writer 和核验 SQL；
- 任务入口沿用项目现有 `template()` 等约定，不另建框架；
- 模块使用分段标题；函数定义前用一句注释说明功能，必要时补充校验、异常或返回约定，不逐行解释普通语法。

### 2.3.1 字段映射排版与维护说明

SQL 左侧显示来源字段或转换，右侧显示目标字段。简短表达式的目标别名放在右侧同一列，行尾注释在合理范围内对齐；长表达式适当分行，在结束处写目标别名。长说明放在对应表达式前，不为对齐制造过宽行或大量空格。

```sql
RTRIM(SOURCE_UNIT)          AS "SOURCE_UNIT_CODE",  -- 来源单位代码
RTRIM(TARGET_UNIT)          AS "TARGET_UNIT_CODE",  -- 目标单位代码
TRIM(CHAR(AUTH_WEIGHT))   AS "AUTH_WEIGHT",        -- 权重无损转为字符
CAST(
    TO_DATE(NULLIF(RTRIM(INVALID_DATE), ''), 'YYYY-MM-DD')
    AS DATE
)                         AS "EXPIRE_DATE"         -- 空值保持 NULL
```

示例只说明排版，字段和转换以当前 mapping 为准。不得因排版改变字段顺序、SQL 内容或转换语义；在目标编辑器抽样检查，不承诺跨编辑器完全一致。

注释保留字段转换依据、固定值与日期规则、多来源执行顺序及覆盖原因、清理范围、失败影响和重跑注意事项，并指出修改后需要同步检查的位置。核验 SQL 每段写明执行库、统计口径和阻断条件。验收关注注释准确性和维护入口，不以注释数量判定质量。

生成新的 Python 作业或用户明确要求时，使用项目约定中已确认可运行的解释器执行 `-m autopep8 --diff <文件>` 预览格式差异。发现差异时记录为待优化项，只写入日志或结果明细，不参与 `Success`、`Failure` 或退出码判定。决定格式化时，确认差异不改变字段名、SQL、字符串常量、数据精度、编码或迁移逻辑后，才可执行 `-m autopep8 --in-place <文件>`。格式化后检查实际差异。新生成或实际修改 Python 后执行一次 `-m py_compile <文件>`；后续迁移前检、执行和校验复用结果，不重复检查未修改文件。默认不使用 `--recursive`、`--aggressive` 或 `--experimental`，不格式化备份、第三方、生成文件或当前任务范围外的历史代码。

`PRE_SQL` 默认保留注释状态的全表清理模板：

```python
PRE_SQL = [
    # f"DELETE FROM {TARGET_TABLE} WHERE 1=1",
]
```

只有确认全量迁移、目标数据允许清理，并取得对应授权后才能取消注释。增量迁移、需要保留已有数据或范围未确认时必须保持注释。

### 2.3.2 多来源执行约束

简单的多来源迁移优先复用现有作业能力；顺序覆盖前核对目标主键及其他唯一约束是否符合已确认判重规则。`replace` 不代表业务规则已验证，也不能代替来源内部重复检查。

存在已授权清理时，目标清理只执行一次；所有来源的必要前检在清理前完成。Shell 按确认顺序调用各来源，任一步失败停止后续写入。顺序直写可能部分完成，操作说明应列明恢复范围与清理影响，不直接跳到后一个来源重跑。不为多来源自动引入辅助表或公共框架。

## 2.4 Shell 入口

采用四段式：任务参数、核心流程、辅助操作、执行入口。

新增脚本的核心流程保留 `precheckMigration`、`runMigration` 和 `validateMigration`。历史脚本中的 `precheck_migration`、`run_migration` 和 `validate_migration` 继续兼容。`main` 只排列执行顺序；单表脚本保持独立，不引用批量 Runner 或公共迁移框架。

`precheckMigration` 先完成不连接数据库的轻量运行条件检查：

- `DATAX_HOME` 已设置、已导出，且 DataX 入口存在；
- Python 项目目录和配置文件存在；
- 当前表的作业文件和作业模块对应；
- 本表实际使用的 Reader、Writer 插件存在。

这些检查只验证路径、文件和进程环境，不重复实现 DataX 或 DASP 的连接逻辑。

每个函数定义前写一句功能注释；终止、清理等关键行为一并点明。辅助函数只在确有复用时保留；`showStep`、`clearStep`、`printResults` 和 `cleanup` 可按实际需要使用。成功、提醒和失败信息由 `printResults` 统一展示，不分别堆叠输出函数。

脚本统一使用 `#!/bin/bash`，同时保持 POSIX Shell 兼容，支持直接执行、`bash xxx.sh` 和 `sh xxx.sh`：

- 用 `. 文件路径`，不用 `source`；
- 用 `[ ... ]`，不用 `[[ ... ]]`；
- 不使用 Bash 数组、`${PIPESTATUS[...]}`、进程替换和 `set -o pipefail`；
- 函数使用 `name()`，不用 `function name`；
- 退出清理使用 `trap cleanup 0`，不用 `trap ... EXIT`；
- DataX 输出先写入日志，再保存真实退出码并展示日志。

文件统一使用 UTF-8 无 BOM、LF 换行，并同时通过 `bash -n` 和 `sh -n` 检查。

## 2.5 执行过程

```text
[1/3] 迁移前检
[2/3] 执行 DataX 迁移
[3/3] 迁移校验
```

- 前检失败时不调用 DataX；
- DataX 可运行在测试、生产或三方环境，脚本不得写死环境；
- 每次执行都必须取得环境、对象、范围和动作的授权；
- 分别保存迁移和校验退出状态；迁移失败保留 DataX 原退出码；
- 迁移成功但校验失败时，整体仍返回失败；
- 统计取自实际结果；使用推算值时写明口径，不把读出条数当成写入成功条数；
- 本阶段不输出单表或整批耗时评估。

迁移执行结果成功时输出一张汇总表。失败时输出执行汇总和错误明细；相同根因合并，完整异常保留在日志中。

```text
迁移执行结果

序号 | 统计项           | 结果
-----+------------------+------
1    | 执行状态         | Success
2    | 迁移成功总条数   | 87
3    | 迁移失败条数     | 0
4    | 失败报错信息     | 无
```

失败时，执行汇总至少包含执行状态、实际成功条数、实际失败条数和错误类型数量；无法取得的指标填写 `未取得`，不得填写 0。错误明细使用“序号、错误类型、错误摘要”三列，不增加“失败阶段”和“影响条数”；失败环节与具体错误合并写入“错误摘要”。无法提取根因时填写“未知错误，详见日志”。

未发起作业或查询记为 `未执行`，查询报错记为 `查询失败`，无法取得指标记为 `未取得`。这些状态不得判定为成功。

交互式终端开始迁移校验前，以不换行状态显示：`正在校验源表与目标表数据，请稍候……`。校验完成或失败后先清除状态行，再输出结果表；日志或重定向输出不显示临时提示。

## 2.6 输出排版

- 多列内容使用表头、分隔线和稳定列宽；
- 标题、表格、错误摘要等大项前后留空行；
- 优先用 `column -t -s '|'` 对齐；不可用时保留带空格的 ` | ` 分隔符；
- 表格过宽时缩短摘要或将完整内容留在日志，不在单表脚本中建设复杂纵向排版；
- 使用单独的 `printf '\n'` 输出空行，避免不同 Shell 的转义差异。

## 2.7 检查与验收

### 2.7.1 完整交付

- 一份 mapping、一个或多个来源 Python、一个 Shell 和一份总核验 SQL 齐全；各作业目标一致，Shell 引用对应作业；
- 新脚本符合命名约定；历史命名只提示，不作为失败条件；
- Python 语法正确；
- 新生成 Python 时可记录 PEP 8 待优化项；该项不作为静态检查的失败条件；
- Shell 同时通过 `bash -n` 和 `sh -n`；
- 文件为 UTF-8 无 BOM、LF；
- Python、Shell 函数都有简短、准确的功能注释；
- 未使用 `SELECT *` 或不兼容的 Shell 语法；
- 查询字段和 Writer 字段数量、顺序、含义一致；
- 每个来源的五列 mapping 与其 Writer 目标字段逐项闭环；字段组或通配行须展开后复核；
- 可静态提取的 SQL 日期参数以样例值离线渲染通过；
- Writer 字段真实存在，必填字段都有来源；
- `PRE_SQL` 默认注释，启用时已有明确范围和授权；
- 未硬编码账号、密码和环境地址；
- 前检表、执行结果表和校验结果表排版清晰；
- 未执行的检查明确标记，不以文本匹配代替运行验证。

从项目根目录运行：

```text
py .agents/skills/datax-table-migration/scripts/check_artifacts.py <目标表目录>
```

加密字段按 [需求规则](requirements.md) 的真实字段清单及逐来源说明核对；静态 transformer 配置只能证明可读取的参数关系，运行时组装和实际加密效果仍需另行验证。

该离线检查逐来源比较 mapping 与 Writer 字段，并比较 `SOURCE_QUERY` / `querySql` 的双引号别名与 `TARGET_COLUMNS` / `WRITER_COLUMNS`；发现查询错位时只报告首个位置和两侧列数。它还以样例日期调用同样的字符串参数替换方式，发现 f-string 提前求值或未转义的日期占位符。不在作业目录生成额外脚本，也不执行 DataX 或数据库操作。

该工具只做离线静态检查，不连接数据库，也不代替迁移前数据检查。整体状态只用 `Success` 和 `Failure`，提醒与未执行项单独记录。必需语法检查不可用时，完整交付检查未完成，不能报告 `脚本生成完成`；已执行检查的通过结果仍保留。

检查器只支持可静态读取的作业常量、标准五列 mapping 和 Shell 中明确的 Python 文件引用。动态 SQL 表达式只检查静态形状；字段组、未识别的参数、SQL 语义、目标实际结构、字段含义、注释准确性及视觉排版需另行复核，不以文本匹配代替验证。完整交付所需检查均完成且通过后，才能报告 `脚本生成完成`。
