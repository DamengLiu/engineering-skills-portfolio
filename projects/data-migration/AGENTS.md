# DataX 数据迁移工作约定

## 1. 项目依据与协作

### 1.1 迁移依据

按交付对象选择主 Skill，项目级权限、通用代码质量和完成判定仍以本文件为准：

- 新建单表迁移：`.agents/skills/datax-table-migration/SKILL.md`，负责需求确认、字段映射和新建交付物；
- 修改已有单表迁移：`.agents/skills/datax-table-modify/SKILL.md`，负责定位问题、修改现有交付物并检查影响；
- 批量迁移：`.agents/skills/datax-batch-migration/SKILL.md`，负责任务编排、日期传递、失败处理和批次结论，不接管单表字段映射。

额外功能需求先由所属场景的主 Skill 明确需求和影响范围，再单独设计；具体修改与验证仍由主 Skill 负责。单表已确认的字段规则以该表当前有效 mapping 为准，不从其他表或历史对话推断。

用户要求新增、更新或修改 Skill，但没有明确指出 Skill 名称或路径，且结合上下文仍不能唯一确定时，必须先向用户确认具体目标。确认前不编辑任何 Skill 文件；不得仅凭最近提及的 Skill、当前任务场景或相邻文件推断目标。确认后只修改用户指定的 Skill。

### 1.2 内容与代码

Skill 内容、`AGENTS.md` 和代码都应像一张清晰的路线图：先交代目的，再展开规则，最后说明边界与结果。

- 语言简洁、准确、自然；一句只表达一个关键意思。
- 结构按逻辑递进：能归并的归并，需区分的分层；标题、编号和列表应帮助读者快速定位。
- `.agents/skills` 中的 Markdown 标题必须反映内容层级并使用连续编号：`SKILL.md` 的一级内容用 `## 1`、`## 2`，子节依次用 `### 1.1`、`#### 1.1.1`；`references` 的文件标题带对应阶段号（如 `# 1 任务定义`），其子节从 `## 1.1` 开始。不得跳级、复用编号或仅因排版加入空标题；新增内容归入最贴近的既有层级，确有独立主题时再增加连续编号。
- 代码与配置遵循最小必要原则：命名清楚、分支克制、注释只解释必要的缘由。
- 以人易读、模型易执行为共同标准；不堆砌术语，不重复规则，不制造隐含前提。

## 2. 执行与输出

### 2.1 执行约定

各模型可以走不同的解题路径，但都遵守同一范围、权限和验收标准。

各主 Skill 按交付场景保持自己的稳定流程，不要求使用相同的章节或步骤。新建单表侧重需求、映射和交付；已有单表修改侧重现象、证据、影响和最小修复；批量迁移侧重任务、调用、汇总和收尾；扩展 Skill 侧重能力缺口、设计和交接。跨场景共用的权限、范围、证据和完成口径以本文件为准。Skill 保留独立执行所需的摘要并引用本文件；专项细则各有明确归属，不多处维护完整副本。

- **定目标，先看终点**：非简单任务先简述目标、修改范围、需保留的行为和验收方式；简单任务一句话即可。这是路线图，不是审批表，已授权且范围清楚就继续执行。
- **沿主线，改动有据**：只做用户要求和完成目标所必需的修改。必要性看“不做是否会做错、做不完，或产生直接运行问题”。分析请求交付结论与方案，执行请求落实已确认方案；实现细节可自主决定，业务规则和范围不自行扩大。新证据要求调整范围时说明直接关联；缺少关键业务决策时只问最少的阻断问题，继续不受影响的工作。
- **留建议，好点子先放旁边**：直接影响当前正确性的纳入处理，独立优化留作建议，说明收益与代价，不顺手实施。“更优雅”“以后可能复用”不能单独成为扩改理由。
- **验结果，用证据说话**：交付前核对改动是否对应任务，业务行为、接口和有效注释是否保留，是否夹带无关重命名、格式化或结构调整。按风险选择检查，分清已验证、未验证和无法验证；局部通过不等于整套完成。
- **到站停，完成就收工**：目标达成、必要检查完成、没有未解决的阻断项时结束任务；可选优化不延长当前工作。

### 2.2 模型选择

模型应服务于任务，而非沿袭会话的起点。

- **默认**：日常、边界清楚的工作优先使用 Luna——能力够用，响应轻快，也更节省 token。
- **升级**：仅在复杂推理、疑难排障、高风险变更，或 Luna 无法可靠胜任时，才升级模型或推理强度；不为简单问题动用重型能力。
- **例外**：用户明确指定模型时优先遵从。若选择明显不匹配任务，应简要说明原因，并建议更合适的配置。
- **边界**：模型选择是建议，执行标准跨模型一致；不为切换模型擅自新建聊天、启动子代理或中断当前工作。

### 2.3 快速执行、时长与 CodeGraph

执行强度应与任务风险匹配，不因任务涉及代码或脚本就默认进行全仓检索、全量构建或高强度推理。

- 明确文件的只读分析、文本修订、静态检查和小范围脚本修改，按模型选择约定优先采用低推理强度。
- 首轮检索使用表名、作业名、字段名或文件名等精确标识，限定目标目录；只有零命中或候选不唯一时才扩大范围。
- 已读取且内容未变的文件，复用当前上下文中的内容，不重复读取；内容发生变化、上下文缺失或有证据表明内容可能过期时，只补读相关部分。
- 相关文件尽量一次批量读取；互不依赖、不会竞争同一资源的只读操作和检查优先并行，并逐项核对结果。存在先后依赖、审批要求或共享资源冲突的操作保持顺序执行；不为并行擅自启动子代理。
- 同一范围的修改集中完成后，只运行一次与实际风险匹配的最低充分检查；文件、相关依赖和检查环境未变时，后续阶段复用检查结果。再次修改、检查失败或出现新的正确性疑点时，只补做受影响的检查；禁止为局部任务运行全仓 lint、format 或构建。
- 预计超过 60 秒的命令，优先选择限定范围的替代检查；预计超过 2 分钟的构建、前检、执行或校验，先说明已知进度和预计范围。除非用户明确要求持续执行，不自动启动该类任务。
- CodeGraph 仅用于入口、调用链或影响范围不明确的跨文件定位。明确单文件或单表任务优先使用精确文本搜索。
- 使用 CodeGraph 前先检查索引状态。存在待同步变更时，其结果只能作为定位线索，不能作为修改或省略验证的依据；不为每次任务自动初始化或同步索引。

### 2.4 表格与终端输出

输出先区分面向人和面向程序的内容，再按载体选择形式。

- **阅读形式**：文档使用标准 Markdown；配置和终端只在比较关系清楚时使用表格，长内容改为分行、列表或独立代码块。
- **排版规则**：列宽取表头与内容的最大宽度，数值右对齐、文本左对齐，列间保留一个空格。中英文混排以项目常用编辑器和目标终端近似对齐，不为适配所有显示环境堆叠空格。
- **机器边界**：配置使用明确分隔符并在解析时去除字段首尾空白；脚本读取退出码或结构化结果，不解析面向人的表格。整体状态只使用 `Success` 和 `Failure`，依据实际错误和本次必需检查是否完成判定；`WARN`、`Skipped` 和待优化项只是明细标签，不直接决定整体状态，可选检查未执行不导致失败。原始信息保留在日志中。
- **验证口径**：字段和值的正确性通过结构化检查验证，视觉效果在目标环境抽样确认；未经实际检查，不声称跨编辑器或跨终端完全一致。

## 3. 代码质量

Python 与 Shell 都应保证意图清晰、行为明确、错误可见和结果可验证。AI 生成的代码不得降低上述标准。

### 3.1 语言选择

- Shell 用于命令编排、环境准备、进程调用、文件操作和退出状态传递。
- Python 用于字段映射、数据转换、结构化解析、复杂校验和需要测试的业务逻辑。
- 当 Shell 出现复杂数据结构、多层嵌套、大段文本处理或难以解释的条件组合时，优先将相应逻辑移入 Python。
- 不为简单调用额外增加 Python 包装层，也不为避免新增 Python 文件而把复杂逻辑塞入 Shell。

### 3.2 共同原则

- 先检查目标文件、相邻实现和调用方式，再进行修改。
- 优先复用项目已有结构、命名、配置入口和错误处理方式。
- 实现应尽量简单、显式、扁平；复杂性确有必要时，应通过职责拆分保持可解释。
- 不猜测参数、路径、字段含义、环境变量、返回格式或外部命令行为。
- 不静默忽略异常、非零退出码或关键校验失败；允许忽略时，应显式说明原因和影响。
- 注释说明业务规则、约束、原因和例外，不重复代码已经表达的行为。
- 可复用固定值优先合并到现有常量模块或配置入口；有限且具有业务语义的取值优先复用或补充枚举。
- 优先合并到职责相近的现有代码；简单功能不得为形式新增实体、结果对象、工具类或分层。

### 3.3 Python

**代码风格与组织**

- Python 代码风格和命名以 PEP 8 为准。
- 函数名、方法名和变量名使用 `lower_snake_case`，类名使用 `UpperCamelCase`，常量使用 `UPPER_SNAKE_CASE`。
- 普通 Python 模块名原则上使用简短的 `lower_snake_case`。
- 代码应直接表达数据来源、转换规则、输出结构和失败条件，避免隐藏副作用和依赖隐式全局状态。
- 函数保持单一职责；优先使用提前返回降低嵌套，不为形式新增类、结果对象或工具层。
- 使用明确的数据结构和异常类型；不得使用裸 `except:` 或宽泛异常捕获掩盖未知错误。
- 必须捕获宽泛异常时，应保留原始异常信息，并明确处理原因和影响范围。
- 文件、数据库连接和其他资源应通过上下文管理器或等效机制可靠释放。
- 新增公共函数或复杂转换逻辑时，应补充必要的类型标注；不得为历史代码批量补充类型标注。
- 可执行脚本的入口逻辑放在 `if __name__ == "__main__":` 下，使核心逻辑可以独立检查或复用。
- 数据迁移 Python 文件名遵循对应 Skill 定义的交付物命名，这是业务对象标识规则；不得据此扩展出其他不符合 PEP 8 的代码命名。

**修改边界**

- 只格式化本次新增或实际修改的 Python 文件。
- 不处理历史文件中与当前目标无关的 PEP 8 问题。
- 不得为了通过格式检查改变字段名称、SQL 内容、字符串常量、数据精度、编码或迁移逻辑。
- 不直接修改生成文件；需要调整时，应修改对应模板或生成程序。
- 未经明确要求，不批量重命名、格式化或改造历史脚本。

**格式化与验证**

- Windows 本地检查使用当前可运行的 Python 解释器（如 `python`）；`py` 仅在能正常启动 Python 时使用。运行前确认解释器版本与本次脚本所需模块，记录实际路径；不要求为离线静态检查创建虚拟环境。
- 某项校验缺少第三方模块时，先看本次任务是否必须运行它；非必需项说明未执行的原因即可。不因此安装依赖或重建服务器环境，也不把某个校验器缺包说成“本地没有 Python”。
- 新生成或实际修改 Python 后，至少执行一次 `<python-bin> -m py_compile <文件>`；后续阶段复用该结果，不重复检查未修改文件。
- 仅在生成新的 Python 脚本或用户明确要求时，执行 `<python-bin> -m autopep8 --diff <文件>`；普通分析、代码阅读和既有脚本调用不运行 autopep8。
- PEP 8 格式差异记录为待优化项，只写入日志或结果明细，不参与 `Success`、`Failure` 或退出码判定。
- 决定应用格式化时，确认差异只涉及安全调整后，才可执行 `<python-bin> -m autopep8 --in-place <文件>`。
- 格式化后必须检查实际差异，并重新执行语法检查。
- 默认不得使用 `--recursive`、`--aggressive` 或 `--experimental`。
- 不得对整个仓库、备份目录、第三方代码或生成文件执行自动格式化。
- 存在相关测试时，再运行与修改范围直接相关的测试。
- autopep8 不可用或检查失败时，应明确记录，但不作为阻断条件；不得在未获授权时自行安装或升级。
- autopep8 和 pycodestyle 只能检查或修复部分代码风格问题，不能验证字段映射、SQL 语义、数据类型或迁移结果。

### 3.4 Shell

**代码风格与组织**

- 脚本声明实际使用的解释器，语法必须与该解释器一致；使用 Bash 特性时明确使用 Bash。
- Shell 函数名和变量名沿用所在目录及对应 Skill 的既有风格，常量和只读配置使用 `UPPER_SNAKE_CASE`。
- 变量、参数和路径默认使用双引号，除非明确需要分词或通配符展开。
- 必填参数、依赖命令、配置文件和目标路径应在执行关键操作前完成校验。
- 关键命令的非零退出状态必须终止流程或进入显式错误处理；不得继续生成可能误导的成功结果。
- 脚本通过退出码或结构化结果判断程序状态，不解析面向人的表格、提示文本或日志文案。
- 使用临时文件或目录时，应确保正常退出和异常退出都能清理。
- 函数变量尽量限制在局部作用域；不得无说明地依赖当前目录、调用顺序或调用者环境。
- 管道和一行命令只用于逻辑清楚的简单操作；复杂步骤应拆开并分别处理失败状态。

**修改边界**

- 只修改完成当前目标所需的 Shell 代码。
- 不顺带重构、批量格式化或改造历史脚本。
- 不直接修改生成文件；需要调整时，应修改对应模板或生成程序。
- 删除、覆盖、全表处理和远程执行前必须校验目标范围，并遵守本文件的权限边界。

**验证**

- Shell 文件至少使用脚本声明的解释器进行语法检查。
- 需要兼容多个解释器时，应分别使用对应解释器检查。
- 环境具备 ShellCheck 时，只检查实际修改的脚本。
- Shell 语法检查只在脚本生成、实际修改或用户明确要求时执行；批量编排、迁移前检和迁移执行不重复检查未修改的单表脚本。
- Shell 静态检查不得触发 DataX、数据库连接或外部环境操作。
- 工具不可用或目标解释器不明确时，应明确说明，不得将代码阅读表述为语法检查通过。

### 3.5 规则优先级

发生冲突时，按以下顺序处理：

1. 用户明确要求和已确认的迁移需求；
2. 数据正确性、运行安全、目标环境兼容性和外部接口约束；
3. 本文件中的通用 Python、Shell 和代码组织规则；
4. autopep8、pycodestyle、ShellCheck 等工具建议；
5. 对应 Skill 中的任务专项规则。

专项规则只能覆盖明确的业务或运行差异，不得无说明地降低通用质量要求。格式化结果与业务语义冲突时，以业务正确性为准，并记录未采用该格式化建议的原因。

## 4. 权限边界

文件修改与数据库操作分别判断授权。“只给 SQL”“不要改文件”不授权文件写入；未授权的数据库查询仍不得执行，已有明确授权的只读查询按其范围进行。生产环境的清理、覆盖、跳过既有记录及重跑行为以当前表已确认规则为准，不因全量或增量模式自动选定。

本作品集仅提供离线材料，不包含测试或生产数据库连接条件；默认只读取代码、配置和日志，生成供目标环境执行的 SQL，不发起数据库连接或连通性试探。需要确认数据库类型时，先沿实际作业的数据源名查当前配置；配置缺失、无法读取或不能确认目标环境所用配置时，向用户确认，不凭数据源名称或常见部署习惯推断。目标环境的实际查询与执行仍须遵守下述授权边界。

### 4.1 可直接进行的工作

读取项目文件、分析映射、编写脚本与本地静态检查。

### 4.2 必须明确授权的工作

连接或查询指定数据库、运行指定 DataX 作业、执行限定范围的核验 SQL、DDL/DCL、全表操作与生产环境操作。

### 4.3 授权的最小边界

授权应同时写明环境、对象、范围和具体动作；不得据此自行扩大操作范围。

## 5. 完成判定

### 5.1 脚本生成

新建完整交付满足以下条件，才可报告“脚本生成完成”；局部修改按实际影响范围验收，不要求补建历史缺失文件：

- 文件齐全，字段、参数与配置对应关系检查通过；
- Python 和 Shell 已按实际修改范围完成对应的最低静态检查；
- 新生成的 Python 代码已参考 PEP 8；遗留格式问题已记录为待优化项，不阻断完成判定；
- 编码、换行、解释器和执行入口符合目标环境要求；
- 实际执行自动格式化时，产生的差异已经人工或模型复核，没有改变业务语义；
- 未执行的检查、执行前提与已知风险均已明确说明。

语法检查、代码风格检查、静态分析和代码阅读不能替代真实运行验证。

### 5.2 迁移执行

只有同时满足以下条件，才可报告“完成”：

- 执行命令正常结束，且 DataX 错误记录为 0；
- 源、目标的字段数量与记录数量符合已确认的对应关系；
- 重复键、必填字段和关键业务字段核验通过。

任一条件未满足，只能报告“未完成”或“执行失败”。
