# 阶段工作法

## 需求澄清

先确认真正影响后续工作的内容：目标用户或操作角色、主流程、成功结果、本期范围、明确不做的内容、关键业务规则和待确认项。将后续能力与当前核心功能分开标记；后续能力不自动阻塞核心功能设计或开发。

当需求来源是多轮对话、历史记录或现有代码时，区分：用户已确认、从现有实现观察到、仍待确认。不要把观察结果写成用户需求。

## PRD 与原型

PRD 从主流程和核心简单功能开始，按需要逐步增加异常流程、框架能力、附加验证或后续规划。每项功能应有可观察的完成结果。

原型主要服务前端，至少说明页面入口、主要操作、页面状态、成功或失败反馈。原型可使用链接、图片路径或文字说明；未有可用原型时如实标注，不伪造页面细节。

## API 与数据模型设计

API 文档仅在接口设计阶段或确需先行明确时建立。记录 URL、请求方法、请求/响应、分页或批量语义、兼容性和待确认项。数据模型文档只在涉及实际存储设计时建立。

框架能力例如权限、双签、幂等、外部系统调用或异步处理，可以在后续阶段设计和实施。发现它们会改变当前已确认的接口、数据或主流程时，记录影响并与用户确认，而不是默认提前实现。

## 分批开发

按能独立说明目标的功能批次组织前后端工作。每批记录：目标、涉及的页面/API/数据范围、完成项、开发自检、遗留项和进入下一批的前提。

开发自检只覆盖当前改动是否具备继续开发的基础，例如构建或静态检查、接口可达、页面能打开、当前保存或查询点可观察。它不是最终功能性测试。

## 最终功能性测试

在全部功能开发完成后，根据 PRD 的核心主流程、扩展流程和已确认边界建立功能性测试记录。明确每项为通过、失败、阻塞或未测，并记录复现条件和结果证据。

当前不要求单元测试。未来用户决定引入时，优先将其写入对应开发批次的计划和记录，按实践逐步扩大覆盖范围。
