# 管理后台功能交付

目标是在不阻塞核心功能开发的前提下，把需求事实、阶段决策和开发进度保存在可续接的材料中。需求材料是后续迭代和生成代码的重要输入，应优先于模型自行推断；用户在当前对话中的明确要求可以更新材料。

本 Skill 面向完整功能或明确功能包。单纯 Bug 修复、样式微调或局部代码修改使用 `mgt-modification`，不强制创建需求档案。

## 需求材料目录

- 默认目录为项目根目录 `docs/feature-records/<feature-key>/`；用户指定目录时使用其目录。
- 需求材料始终保存在项目内，方便统一阅读和管理。该目录供用户自行决定是否加入 `.gitignore`；除非用户明确要求，不修改 `.gitignore`。
- 首次进入一个功能时创建 `index.md` 与当前阶段必要的材料；不要预先生成空文件。
- 小需求可在一个 Markdown 中维护多个章节；随着内容扩大再拆分为多个文件，并从 `index.md` 链接。
- 记录事实、决策、范围和验证结论，不粘贴长日志、完整命令输出或大段源码。

使用 [需求材料布局](references/artifact-layout.md) 选择文件和模板。需求澄清或 PRD 工作读取 [阶段工作法](references/phase-workflow.md)。
规划功能范围、拆分开发批次或需要复盘相似演进时，才读取 [分阶段交付样例经验](references/phase-delivery-experience.md)。

## 阶段与顺序

按当前项目实践推进，阶段可在真实需求变化后调整；每次调整在 `index.md` 的变更记录中说明影响范围。

1. **需求阶段**：澄清关键点，维护主流程、核心简单功能、本期范围和待确认项；PRD 可逐步补充后续框架能力或附加流程。原型主要描述前端页面、交互和关键状态。
2. **设计开发阶段**：先按实际需要设计 API 和数据模型，再前后端分批实施。框架能力允许后续设计和实施，不作为首批核心功能的默认阻塞条件。
3. **测试验证阶段**：在全部功能开发完成后进行完整功能性测试。单元测试按目标项目要求安排，可随开发批次逐步加入；不得用开发自检代替最终功能性测试。

开发批次中的编译、接口可达、页面可运行和当前改动点检查属于开发自检，不称为完整功能性测试，也不替代最终测试。

## 运行规则

1. 先确定功能标识、当前阶段、已有材料和本次目标；续接时先读 `index.md`、相关需求材料和当前 Git 差异，再根据源码核验会影响本次工作的事实。
2. 需求不完整时，先记录“待确认”和它阻塞的决定；只有缺失信息会导致错误实现时才向用户询问。
3. 需求有实质变化时，可直接更新源需求文档，并同时记录变化原因、影响阶段和未完成调整；不得静默保留已失效的结论。
4. 设计或开发实际涉及页面、接口、权限、双签、幂等、外部调用时，使用 `mgt-modification`；涉及数据模型、字段、字典、索引或复杂 Mapper 时，使用 `database-design`。本 Skill 不复制这些专项规则。
5. 未获得实施授权时，只更新需求或方案材料，不修改业务代码、数据库或外部系统。
6. 每个开发批次记录目标、涉及范围、已完成项、开发自检和遗留项；最终功能性测试只在测试阶段记录。

## 完成与续接

`index.md` 必须能回答：需求当前是什么、处于哪个阶段、已完成什么、下一步是什么、哪些结论仍待确认。功能完成后保留材料作为下一次迭代的输入；用户要求技术复盘或发布笔记时，再按目标项目的文档流程处理。
